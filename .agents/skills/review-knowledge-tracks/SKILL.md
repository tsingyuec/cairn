# 检查知识脉络

## 适用场景

- 用户要求“检查/复审/审计某条脉络”“看看还缺什么”“看看顺序对不对”“检查 REUSE 和前置”。
- 新增一批单元后，确认主线是否仍闭合、编号和链接是否仍可读。
- 准备写作或认领任务前，确认该脉络的课程路径、证据边界和范围声明。

不适用于：新增模型/资源、拆分脉络、批量改写正文。新增内容转 [extend-knowledge](../extend-knowledge/SKILL.md)；本 skill 只负责检查和记录，修复必须得到用户明确授权。

## 开始前

1. 以本 skill 目录为基准，项目根目录是 `../../..`。先读根 `README.md`、`content/README.md`、目标脉络所属分类 README。
2. 读目标脉络 README 全文，不只看目录；再读 [学习单元粒度规则](../extend-knowledge/granularity.md) 和 [整合式章节目录规则](../extend-knowledge/curriculum.md)。
3. 读该脉络上一轮复审记录（`docs/目录审查/` 下的对应报告和明细），避免重复报告已经落地的项；未落地的项要明确标出。
4. 读该脉络所有 `[REUSE]` 指向的 B/M 小节，确认它们真实存在、是自有任务、且内容对应当前用途。
5. 读相邻脉络的 README，尤其是同一科学问题的其他 P/D 脉络，用于判断重复、错位和归属。
6. 记录快照：脉络代码、小节总数、自有任务数、REUSE 数、最大编号、状态分布、当前 Git 工作区是否干净。审查期间不要改文件。

## 审查流程

### 1. 重建主线

先用一句话写出该脉络的科学主线，再列出主线上的必要环节。不要从现有小节反推“已经有什么”，而要独立回答：

- 研究对象是什么，输入输出是什么，测量/观测单位是什么？
- 从对象到结论需要哪些表示、机制、算法或资源？
- 哪些环节需要实验或外部证据验证？
- 哪些是共享基础，哪些是该脉络特有的机制？
- 该脉络的边界在哪里，什么不属于它？

B/M 脉络的主线通常是“概念 → 机制 → 计算/测量 → 判读”；P 脉络通常是“任务 → 表示与条件 → 方法谱系 → 机制案例 → 评价与验证”；D 脉络通常是“原始对象 → 发布与版本 → 标识与坐标 → 证据与许可 → 任务适配”。

### 2. 检查章、节、小节的结构与顺序

- 每一章是否对应主线上的一个完整环节，而不是模型清单或字段清单？
- 每一节是否有明确的学习对象；节标题是否能覆盖其下所有小节？
- 前置是否先于使用：数学、统计、生物学概念、文件格式、评价协议是否在需要之前出现？
- 是否存在前向引用、循环前置、跨章跳跃，或“先讲结果再补定义”？
- 是否有空节、单小节节、标题与内容不匹配的节？
- 编号是否连续，锚点是否唯一，章/节/小节层级是否正确？
- 小节数量是否少于 100（按叶子脉络计，含 REUSE；分类和项目总数没有 100 上限）？

### 3. 检查主线完整性

按“可命名的缺失单元”判断，不按数量判断。每个缺口必须能写出：

- 缺的是什么知识单元（不是“这里不够深”）；
- 应插在哪个锚点/小节之后；
- 为什么它是主线必需，而不是可选扩展；
- 有什么证据（官方文档、论文、资源发布、既有课程缺口、相邻脉络已覆盖而本脉络未覆盖）。

重点检查六类常见缺口：

1. **主线整块缺失**：从对象到结论的某个必要环节完全没有。
2. **方法谱系偏窄**：只列少数模型，缺经典/统计/非神经路线或对照方法。
3. **机制深度不足**：只有输入输出和风险提醒，没有表示、训练目标、采样/推理或评价。
4. **评价与验证缺位**：没有基线、切分、校准、外部验证、失败模式或实验衔接。
5. **生物学/数据前提缺失**：没有实验单位、测量条件、标识符、版本或许可边界。
6. **前置悬空**：使用了未讲的概念，或 REUSE 指向了不存在的具体小节。

如果主线已经闭合，明确写“否，未发现整块缺失”，不要为了凑数制造缺口。局部缺口与整块缺失分开记录。

### 4. 审计 REUSE

REUSE 是课程内容类型，不是进度状态。逐条检查：

- 来源是否是**自有 B/M 任务小节**，不是整门课、不是另一个 REUSE、不是 P/D 专题。
- 是否指向具体叶子锚点，链接可打开，标题与用途一致。
- 是否放在使用之前；同一脉络内是否重复引用同一来源。
- 学习目标是否说明“从来源取什么、在本脉络怎么用”，而不是“掌握基本定义”。
- 是否计入本脉络规模（是），是否被误算为任务（否），是否被认领/标状态（否）。
- 是否真的需要 REUSE：如果本脉络有该知识点的特有扩展，应保留自有任务；如果只是重复 B/M，改为 REUSE 或收窄。

### 5. 检查标题与学习目标

标题：

- 名词性知识主题，直接写对象、机制、术语或判读对象。
- 不写“如何/怎样/为什么/什么/哪里/从何/读懂/学会”等问句或教学指令。
- 不把多个独立机制用逗号硬拼；也不为凑统一格式强行加冒号。
- 不 overclaim 专有模型的内部细节；没有官方证据的机制写成证据边界，不猜测。

学习目标：

- 3–5 个可验收检查点：说明/比较/判断/识别/把……联系起来。
- 不用“掌握「…」的基本定义和关键关系”“给出与本节范围一致的解释或案例”“细节以原节为准”等模板句。
- 目标要能区分“读过”与“会用”：包含边界、失败模式、与相邻单元的衔接。
- 目标中的编号引用必须指向当前编号；改号后要同步修复。

### 6. 检查重复与错位

- 同一机制是否在 B/M 与 P/D 各写了一遍？确定唯一主归属，其他位置改 REUSE 或收窄。
- 同一模型是否在多个专题重复讲同一模块？按“谁负责该科学问题”划分，不按模型名划分。
- 是否有单元放错章/节：例如评价单元夹在训练节、数据任务挂在标识章、资源许可放在字段说明里？
- 是否有“模型资料/版本说明/免责声明”被拆成独立小节，挤占教学单元？
- 是否有单元只是字段、命令、端口或部署步骤，而不是可独立理解的知识点？

### 7. 检查范围与学习出口

- “范围与边界”是否与目录实际内容一致：新增了别构口袋、mRNA 设计、受控访问或许可，就要在范围声明中写明；排除了 gnomAD 等对象，也要写明边界。
- “前置知识”是否真实：如果写“无需先读上游”，但目录中大量 REUSE 指向 B/M，应改为“所需通用知识已在使用处编入”。
- “学习出口”是否指向有依据的下一站，而不是随手链接一个相邻专题。
- 是否有范围问题需要用户先决定（纳入/排除/归属），不要自行替用户决定后直接补单元。

### 8. 记录证据边界

- 区分“目录级判断”与“科学事实已核实”。审查通常只读 README、规则、REUSE 目标和相邻目录，不等于读完论文、代码或视频。
- 专有模型（RFD4-Proteina、ABFT、ABDP、LocateAnything、MolMIM 等）的内部细节，没有官方资料就标证据缺口。
- 资源许可、版本、数据使用协议、实验结论，未核对官方发布就标“待核对”。
- 不把静态校验通过说成科学正确或教学充分。

### 9. 分级与报告

把发现分为四类，写入报告：

- **A 结构问题**：顺序、错锚、重复、空节、内联前置、标题与内容不符。通常 0 新增。
- **B 实质缺口**：缺失的知识单元、方法谱系、评价环节、数据前提。每个缺口给插入位置和证据。
- **C 范围问题**：纳入/排除/归属需要用户先决定的事项。
- **D 目标/措辞**：模板目标、问句标题、过度声明、编号引用错误。

报告模板见 [report-template.md](report-template.md)，逐项检查清单见 [checklist.md](checklist.md)。单条脉络的报告控制在可读范围；28 条批量复审时，每条先写独立报告，再写聚合报告。

### 10. 修复（仅在用户授权后）

默认只读。用户明确要求修复后：

1. 先修 A 类，再补 B 类 REUSE，最后补 B 类自有任务；C 类先问用户。
2. 使用 `_work/renumber.py` 的 plan 机制，不手工静默改号：
   - plan 定义 `DATE`、`DESCRIPTION`、`LEDGER`、`EDITS`；
   - `op='insert'` 支持 `kind='task'|'reuse'`、`after='X.Y.Z'|'#id'|'start:X.Y'`；
   - `op='move'` 用 `from` + `after`；
   - `op='update'` 改 `title`/`goal`/`kind`/`status`/`source`；`source` 用 `('M03', '3.2.2')` 这样的代码+编号，不是路径；`kind='task'` 会清空来源，不要再传 `source`。
3. 先不带 `--apply` 预览，检查 `_work/renumber-preview` 的编号、顺序、REUSE 来源和空节；确认后再 `--apply`。
4. 每轮生成独立 ledger，不覆盖历史映射；把新 ledger 追加到 `tests/test_migration.py` 的 `cls.supplements`。
5. 改号后搜索所有入链并修复；`renumber.py` 会重写项目内链接，但仍要人工抽查跨文件引用。
6. 更新 `content/README.md`、分类 README、根 README 的统计；不要只改总数，逐条核对每脉络小节数。
7. 不自动提交、推送、部署或生成博客；除非用户明确要求。

## 验证命令

在项目根目录执行：

```bash
python3 scripts/validate.py
.venv/bin/python -m unittest discover -s tests
node scripts/check/check_md_math.mjs content
.venv/bin/python site/build_site.py --check
.venv/bin/mkdocs build --strict
node scripts/check/check_katex.mjs build/site --recursive
```

`validate.py` 至少应报告：28 条脉络、当前小节总数、链接数、自有任务数、REUSE 数、WAITING 数。测试、站点构建和公式检查通过只代表静态一致性，不代表科学或教学充分。

## 快速自检

- 我是否先重建了主线，而不是只对着现有目录找缺口？
- 每个“仍缺”是否都能命名、定位、给证据？有没有为了数量制造缺口？
- 我是否区分了整块缺失与局部缺口？
- 我是否检查了 REUSE 的来源、位置、目标和重复？
- 我是否检查了标题的问句化、模板化和过度声明？
- 我是否检查了范围声明与学习出口？
- 我是否把“没读论文/视频”写进了证据边界？
- 如果结论是“完整”，我是否明确写了“否”？
